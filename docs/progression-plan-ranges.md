## Model and behavior

Simple programs keep their existing assignments and workflow. Exact/range numeric parameters are universal in the existing prescription editor, including library defaults, patient-specific assignments and plan overrides. Old `{value,unit}` objects remain exact. A range is `{mode:"range",value:null,min,max,target?,unit}`; `value:null` prevents old exact-dose projections from inventing an actual/target dose. Validation enforces units, finite nonnegative values, whole counts/frequency, field-specific limits and min ≤ target ≤ max. Legacy ambiguous strings remain unchanged and require clinician review.

The optional collapsed Progression Plan has compact Exercises | Weekly | Daily views. A document contains optional phases, reusable day templates and ordered weeks. Phases carry name, focus, goal, optional start/duration, advancement criteria and notes. Weeks select templates and optionally override individual numerical prescriptions. Recovery is an explicit label, never an automatic load reduction. Copying a week or template creates a draft copy; it never approves numerical changes or mutates the Exercise Library.

Every saved draft/approval is an immutable `program_progression_revisions` row. One approved revision is attached to the program; only its chosen active week is available to patients. Advancing weeks/phases requires another clinician review and explicit approval. There is no date-triggered advancement or universal clinical rule. Approving return to the simple program appends history and removes current plan availability without deleting records. Existing assignment history remains in `engine_program_changes`.

Templates reference stable assignment IDs, retaining approved videos and exercise identity. Each template has independent FITT, notes, prior-exercise prerequisites, fixed weekdays or an exact/range weekly target, scheduled-only restrictions and minimum recovery hours. Week overrides apply to a template/assignment pair. Base prerequisites remain required. Template prerequisites point backward to prevent cycles. Removing an assignment used by the active plan is blocked pending plan review.

Patients choose an approved template, a suggested date in the active week, then Full / Individual / Section selection. Each exercise still requires its own Done. Scheduled-only rules and recovery spacing are enforced in the database on confirmation, including legacy insertion attempts, not just by disabled controls. Flexible targets are guidance; they do not impose an invented hard cap or automatically escalate dose. A future-suggested exercise can be reported today if unrestricted: its planned date remains separate from the server-recorded performance timestamp and declared timezone.

Done confirms reported activity without guessing actual sets/reps. Optional Adjust what I did supports exact numerical actual dose and per-set repetitions. `10,8,8` with 3 sets × 8–12 reps remains completed reported activity, never automatically partial/failure. Actual dose cannot itself contain ranges. Per-set counts validate before database integer conversion; explicit actual set count must match array length. Actual scalar reps and per-set counts cannot conflict. Omitted values stay unknown. Reports/snapshots identify self-report, original prescription/revision/template, scheduled and performed dates. Logs remain immutable and retry-idempotent; separate sessions can report activity independently.

Upper-range insights require at least two records containing observed repetitions and retain source record IDs. They only invite clinician review, explicitly leaving missing symptoms, difficulty, movement quality and function unknown. They never change a prescription or infer adherence from Done. Existing clinician Today/summary/progress counts and three-day follow-ups continue to use individual activity evidence; selecting a week/day/section is not activity.

## Migration, authorization and compatibility

`20261024211010_progression_prescription_ranges.sql` is additive except replacing the shared prescription validator and confirmation function with compatible supersets. No historical dose/range is inferred or backfilled. New revisions use relationship-based RLS, no anonymous access, insert/select-only grants and clinician/version validation. Patient-visible rows are approved revisions only; unrelated clinicians/admins cannot read or approve. Approval and publication occur transactionally under the program lock, with optimistic version checking. RPCs are SECURITY INVOKER with empty search paths. Approval history and confirmed actual activity are immutable.

Confirmation preserves the existing server snapshot and trusted provenance and overrides only the approved day prescription/cues. Patient activity is serialized across sessions before checking recovery spacing. Session plan/date/timezone choices are immutable. A changed program blocks further new confirmations against a stale session, while retries of a committed confirmation return the original ID. Clinically restricted programs reject legacy writes that lack an individual selected session.

Application previews for `feat/progression-prescription-ranges` clear browser Supabase settings and server database secret, preserving production. `/workflow-preview` uses only synthetic in-memory data. Browser-to-database tests use a local PostgreSQL/PGlite fixture with a simulated Auth/PostgREST adapter; they do not prove hosted Auth or physical-phone behavior.
