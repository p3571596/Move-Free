# Patient-directed exercise workflow — integration review

Base inspected: main `c96eeed36db8564807fb2bd8ccb305ad4b688088`, also verified as the READY production deployment on October 20, 2026. Work is isolated on `integration/patient-directed-workflow`. No production schema change, merge, or deployment is authorized by this change.

## Behavior

Patients can Follow Full Program, Choose Individual Exercises, or Select Section(s). Selection creates an immutable, resumable session list and never exercise activity. Clinically required preparatory exercises are included in the list. Patients can open any unrestricted exercise, move Next/Back without recording anything, return to the list, leave, resume after reload, close a session, and start another on the same day.

Done saves just that exercise immediately. Its record means patient-confirmed activity, **not completion of the full prescribed FITT dose**. Optional Adjust what I did captures numerical sets, reps, duration, intensity and resistance with units. Unspecified actual values remain unknown. The server captures the prescribed numerical values, original legacy instructions, notes/cues and assignment identity separately. Program changes after session start reject new confirmations; close the old session, reload, and start a new one. Historical records are not rewritten.

Optional difficulty, symptoms and comments remain available. A hidden-details action allows an explicit report of nonperformance; it creates `activity_source=explicit_nonperformance`, never confirmed activity. Leaving, moving past or deselecting an exercise creates neither a skipped nor a failed record. Historical partial/skipped reports retain their original meaning; no missing record is backfilled as nonperformance.

Progress uses recorded counts and sessions with records. The Patient Log shows source and actual values. Clinician Today retains symptom/difficulty and explicit nonperformance exceptions, feedback-to-review and inactivity; it no longer invents an adherence percentage from only submitted exercises. Engine evidence retains source record IDs and prescription snapshots; no recorded-count percentage supplies prescribed adherence. Existing three-day follow-up scheduling and cooldown remain; session selection alone does not trigger or reset activity.

Clinicians can set required full order or prerequisites among earlier assignments in Program Builder. Settings save separately after program edits, with an optimistic version check; patient treatment edits remain denied. Both the UI and database enforce required confirmations within the same session. Prerequisite cycles and invalid ordering are rejected.

## Data and security

`20261020202607_patient_directed_sessions.sql` is additive. Existing programs default to flexible order and empty prerequisites; historical logs retain `legacy_report`, unknown actual dose, and existing snapshots. The migration never fabricates historical dose or performance. No old UUID session IDs are converted into new selections. New sessions have RLS, minimal grants, no anonymous access, ownership-checked writes, and treating-relationship reads. RPCs use SECURITY INVOKER and an empty search path. Confirmation takes a session lock, returns an existing result on retry, and retains the existing unique patient/session/exercise index. Closed-session retries return the existing confirmation; closing is idempotent. A program lock plus version check prevents recording against a silently changed prescription. Active assignment and current patient ownership are checked. Existing approved-private-video reads, signed playback, clinician publication and account allowlists are preserved.

Branch preview is deliberately synthetic-only: Next config clears browser Supabase connection and server secret for this branch in Vercel Preview. `/workflow-preview` demonstrates the real UI with disposable in-memory data. Database-backed browser testing uses a local PostgreSQL/PGlite fixture and PostgREST transport adapter; it does not connect to the shared production database. A hosted authenticated Supabase smoke test remains a release gate in a separately approved isolated database. Do not point this preview at production to test an unapplied migration.

Keep rollout coordinated to avoid cached old clients showing obsolete completion language.
